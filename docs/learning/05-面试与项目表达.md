## 一、业务与架构

### 1. 用一分钟介绍这个项目

**参考回答：** 项目面向电商经营复盘、库存诊断和竞品研究。它用确定性工具计算经营指标，用受限模型组织研究与报告，并保存可回查的证据。FastAPI 负责认证与任务登记，Worker 从数据库领取任务，LangGraph 管阶段与恢复，Deep Agents 在满足条件的公开研究中负责工具选择和可选专家委派。React 展示进度、依据、复核和下载。

**源码依据：** [API](../../app/api/server.py)、[Worker](../../app/tasks/worker.py)、[主图](../../app/research/graph.py)、[业务工具](../../app/commerce/service.py)。

**继续追问：** 为什么不把所有工作放在一个聊天请求中？

**回答边界：** 当前定位可复现学习、展示与小规模试用，生产环境尚未完成验收。

### 2. 为什么既有 LangGraph，又有 Deep Agents？

**参考回答：** 主流程的阶段、权限、预算和交付规则应由程序控制，LangGraph 负责计划到导出的编排与检查点。需要灵活选择公开资料检索、读 Skill 或委派时才进入 Deep Agent。Agent 循环在主图的 collect 内，不能改变整个任务的授权范围。

**源码依据：** [build_workflow/collect](../../app/research/graph.py)、[create_researcher](../../app/research/agents.py)。

**继续追问：** 只有库存来源时会进入 Deep Agent 吗？

**回答边界：** 不会；当前还要求 live、web 来源、公开词和非 workflow 策略。

### 3. workflow、single、multi 怎么比较？

**参考回答：** workflow 是按授权词确定性采集的基线，single/multi 满足条件后进入研究 Agent，multi 还配置限定来源的专家。三者共用业务工具、归纳、报告和校验。比较收益需要相同配置、独立重复轮次、人工标签、成本和实际委派记录；不能因配置了多个专家就宣称更好。

**源码依据：** [create_researcher](../../app/research/agents.py)、[compare_runs](../../evaluations/review.py)。

**继续追问：** workflow 也可能调用模型吗？

**回答边界：** live 下的规划、归纳、报告与评审仍可能调用模型；当前多 Agent 收益未完成真实对照验证。

## 二、异步任务与恢复

### 4. 提交返回 202 保证什么？

**参考回答：** 保证任务通过准入并已登记，不保证报告已完成。`create_task` 校验会话归属、幂等、活跃上限，提交任务和 queued 事件；后台 Worker 之后领取并执行。

**源码依据：** [server.start](../../app/api/server.py)、[Repository.create_task](../../app/storage/repository.py)。

**继续追问：** 网络超时后怎样确认是否已经登记？

### 5. 幂等键与请求哈希为什么都需要？

**参考回答：** 幂等键标识同一次客户端提交尝试，请求哈希防止同键被复用于不同内容。同用户同键同请求返回原任务；内容不同返回冲突。数据库唯一约束兜底，不能只依赖前端禁用按钮。

**源码依据：** [App.submit](../../frontend/src/App.tsx)、[Repository.create_task](../../app/storage/repository.py)、[Task](../../app/storage/models.py)。

**继续追问：** 刷新后再点提交一定复用原键吗？

**回答边界：** 前端 pending key 在内存中，重载后不保证复用；内容相同但新键仍可能建新任务。

### 6. 多 Worker 怎样避免领取同一任务？

**参考回答：** PostgreSQL 领取事务用 `FOR UPDATE SKIP LOCKED` 锁定可领取行，再按旧 token 和状态条件更新，成功后生成新的随机租约 token。执行中的写入还检查 token、期限与状态，不能只在开始检查一次。

**源码依据：** [Repository.claim/_fenced/validate_task_lease](../../app/storage/repository.py)。

**继续追问：** SQLite 为什么不能直接证明这些 PG 并发语义？

### 7. 已经保护业务写，为什么还要保护检查点？

**参考回答：** 旧 Worker 如果还能覆盖检查点，新的执行者可能沿陈旧进度继续。LeaseFencedSaver 把 checkpoint 和 pending writes 都纳入租约检查，检查到写完持续持有任务行锁，并限定线程属于当前任务。

**源码依据：** [LeaseFencedSaver](../../app/tasks/checkpoints.py)、[fencing 测试](../../tests/test_checkpoint_fencing.py)。

**继续追问：** 这是否把业务表和检查点变成了一个事务？

**回答边界：** 没有。Saver 有自己的提交，跨业务库、检查点和文件仍存在崩溃窗口。

### 8. 为什么不承诺 exactly-once？

**参考回答：** 节点内外部请求完成但检查点未持久化就崩溃，恢复时可能重发；租约只能拒绝失效执行者的本地提交，无法撤销已经发出的服务请求。项目用证据去重、产物按任务和名称登记、租约目录与检查点降低重复影响，执行语义仍需按至少一次理解。

**源码依据：** [Worker](../../app/tasks/worker.py)、[add_evidence/add_artifact](../../app/storage/repository.py)、[恢复测试](../../tests/test_recovery.py)。

**继续追问：** 同步持久化能消除节点内部全部重复吗？

### 9. 人工复核怎样跨进程恢复？

**参考回答：** 图在 review 通过 interrupt 保存中断进度，Worker 将任务标为 waiting_review。API 保存批准或驳回并重新排队，新 Worker 用同 thread_id 和 Command.resume 继续。批准才导出，驳回结束，不需要维持一个长期审批 HTTP 请求。

**源码依据：** [graph.review](../../app/research/graph.py)、[Repository.review](../../app/storage/repository.py)、[Worker.process](../../app/tasks/worker.py)。

**继续追问：** 为什么 interrupt 之前不宜放不可重复的副作用？

### 10. 取消、服务读取超时、任务总时限有何区别？

**参考回答：** 取消是用户意图，通过持久化 cancelling 通知 Worker；读取超时约束请求等待响应数据的无活动时长；任务总时限由持久化 deadline 和 Worker 的 asyncio.timeout 控制。心跳与租约检查保证取消或过期执行者不能继续提交受保护结果。

**源码依据：** [cancel/claim](../../app/storage/repository.py)、[Worker.process](../../app/tasks/worker.py)、[model_from_settings](../../app/research/agents.py)。

**继续追问：** asyncio 取消后线程里的 PDF 处理一定立刻停吗？

**回答边界：** 不一定，已经开始的底层线程可能继续；后续登记仍需检查租约和状态。

## 三、业务事实与模型可靠性

### 11. 为什么模型不负责计算销售额？

**参考回答：** 销售额和库存覆盖有明确口径，用固定 SQL、整数分和 Decimal 更容易复算与测试。模型选择事实、解释与建议，经营数值通过完整指标引用进入程序渲染的事实句，避免自由文本把数字安到错误商品上。

**源码依据：** [sales_summary/inventory_risks](../../app/commerce/service.py)、[render_bound_metrics](../../app/research/evidence.py)。

**继续追问：** 净销售额和净利润差在哪里？库存覆盖是预测吗？

### 12. 为什么数字存在于证据还不够？

**参考回答：** 同一个数可能属于另一商品、单位或周期。MetricReference 绑定 evidence_id、key、value、entity_id、unit、period 和快照，校验后按事实目录渲染。只检查数字集合会放过错配。

**源码依据：** [MetricReference](../../app/research/schemas.py)、[metric_binding_issues](../../app/research/evidence.py)、[quality 反例](../../tests/test_quality.py)。

**继续追问：** 绑定通过能不能证明后面的分析成立？

**回答边界：** 不能，因果、业务推断、资料真伪仍需独立核验。

### 13. 为什么要区分缺失数据和零销量？

**参考回答：** 没有记录可能是数据没导入，不能解释为真实零。工具用预期商品日记录与实际记录判断完整性；缺日期或没有正净销量时不估计库存覆盖。前期不完整或金额基数非正时不计算变化率。

**源码依据：** [_sales_period/sales_summary/inventory_risks](../../app/commerce/service.py)。

**继续追问：** 商品中途上架时，当前完整性假设有什么局限？

### 14. 有逐字 quote，研究发现还会错吗？

**参考回答：** 会。原文可能被跨句拼接，件数可能误读成金额，互补规则也可能误判为冲突。程序先校验 quote 和来源，再让模型对每条 finding 返回意见，且完整覆盖所有 ID。评审仍可能误判，所以重要结论还需人工逐项核对。

**源码依据：** [validate_synthesis/research_review_issues](../../app/research/synthesis.py)、[语义反例](../../tests/test_research_semantics.py)。

**继续追问：** 漏了一条发现的评审，能不能默认为 supported？

### 15. 为什么要保存证据选择清单？

**参考回答：** 账本可能比模型上下文大，截断和来源分配会影响模型实际看到的内容。manifest 保存选中、排除、窗口与截断，便于回查“原文有，但模型是否真的看到了”。它提高可审计性，不能保证召回充分或推理正确。

**源码依据：** [evidence_package](../../app/research/context.py)、[graph.export](../../app/research/graph.py)。

**继续追问：** 当前库存包和文本窗口各有什么上限？

### 16. 研究失败后为什么不直接强行生成结论？

**参考回答：** 研究候选最多业务修正一次，仍不过就保留确定性摘录并记录研究失败。报告有独立校验和回退路径。这样即使文件可交付，也不会把未通过的研究结论包装成已验证结果。

**源码依据：** [reviewed_synthesis](../../app/research/synthesis.py)、[graph.validate/export](../../app/research/graph.py)、[评估门槛](../../evaluations/run.py)。

**继续追问：** degraded 是否必然表示用了模板？

**回答边界：** 不必然。范围限制也会 degraded，要另看 draft_fallback_used、fallback_used 和研究验证。

## 四、权限、费用与验证

### 17. Agent 为什么不能自己传 tenant_id 或搜索任意词？

**参考回答：** 身份由登录用户和 Worker 的 RunContext 绑定，工具参数不接收可扩大权限的 tenant。公开查询只能逐字来自用户单独提供的列表，端点由程序固定；内部材料不能通过模型拼接成公开关键词。这些由 Gateway 强制执行，Skill 和提示只是补充。

**源码依据：** [authenticate](../../app/core/auth.py)、[RunContext](../../app/storage/repository.py)、[ToolGateway](../../app/research/tools.py)。

**继续追问：** 内部附件与组织规则的检索范围有什么不同？

### 18. 怎样控制模型费用，为什么未知回执后停止？

**参考回答：** 在模型 callback 的请求开始前检查次数、Token 阈值和租约，覆盖 SDK 内部摘要等调用；返回后校验非负整数回执。缺失、非法或崩溃未回执会把任务标为用量不完整，停止后续新请求，不用零费用掩盖未知。Token 阈值按已返回用量检查，不是绝对账单封顶。

**源码依据：** [RuntimeModelMeter](../../app/research/meter.py)、[consume/record_usage/account_unreported_usage](../../app/storage/repository.py)。

**继续追问：** 后续一份有效回执能恢复整条任务的可信状态吗？

### 19. 为什么“有测试、有 CI”还不能说生产可用？

**参考回答：** 每种验证覆盖不同范围。离线契约、SDK 替身、真实隔离 PG、浏览器 demo 和模型单例都需要分别解释。当前真实搜索/RAGFlow、多 Agent 收益、模型稳定性、目标服务器 HTTPS 与生产恢复仍未完成验收。

**源码依据：** [交付记录](../18-python-delivery-validation.md)、[模型记录](../16-usage-receipts-and-provider-check.md)、[CI](../../.github/workflows/ci.yml)。

**继续追问：** 你能拿出哪条原始请求、证据和人工核验记录？

**回答边界：** 187 条后端、32 条离线、三个真实单例、20 任务教学负载是不同批次和范围，不是生产成功率。
