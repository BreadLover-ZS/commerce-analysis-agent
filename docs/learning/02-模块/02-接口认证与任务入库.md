## Part B：登录态、CSRF 与业务归属

`sign_in → login` 校验密码，生成随机 token。浏览器 Cookie 保存 token，数据库 `AuthSession` 保存 token 的哈希与到期时间。密码使用带盐 PBKDF2；Cookie 不是 JWT，也没有让客户端自己声明 tenant。

`authenticate` 读取 Cookie、查会话、查用户；对非 GET/HEAD/OPTIONS 请求还检查 Origin 和 `X-CSRF-Token`。前端通过 `setAuth` 保留登录响应中的 CSRF 值，`api` 自动附加；浏览器负责发送 HttpOnly Cookie。

```text
Cookie → AuthSession → User → CurrentUser
                                  ↓
                   user.id / user.tenant_id
                                  ↓
                 create_task / 资源归属查询
```

这与 Java 中“从服务端登录态取得用户”的职责相近。CSRF 解决请求伪造，资源归属解决访问别人的任务，租约解决执行者是否仍有提交权，三者不能互相代替。

`GET /api/tasks/{task_id}` 按当前用户检查；证据和事件接口先检查任务归属。下载则取得 Artifact，校验安全路径与文件存在，再检查其任务归属。当前下载接口没有逐次重算哈希；文件哈希核对在负载与恢复演练等验证入口完成。资源不存在或不可访问统一返回 404，不向越权访问者确认别人资源是否存在。

## Part C：`create_task` 分四段阅读

### C1. 请求指纹

请求先转成 JSON 兼容字典，排序序列化后计算 SHA256。指纹表示本次请求内容，幂等键表示客户端认为是同一次提交尝试。

| 情况 | 当前行为 |
| --- | --- |
| 同用户、同键、同请求 | 返回已有任务 |
| 同用户、同键、不同请求 | `Conflict`，HTTP 409 |
| 相同内容、新键 | 按新任务处理，仍受活跃上限约束 |

幂等不等于“相似问题永久只分析一次”。

### C2. 串行准入和范围检查

PostgreSQL 下锁住当前 User 行，让该用户并发准入按顺序检查。随后检查会话属于当前用户、活跃任务数未达到限制。这里锁用户是为准入；Worker 领取任务锁的是 Task 行。

### C3. 写任务与排队事件

新任务保存 `user_id/tenant_id/conversation_id/parameters/mode/request_hash`，并写 queued 事件，一次事务提交。mode 在任务建立时保存，执行时继续遵守，防止配置切换把已排队 demo 变成付费 live。

### C4. 唯一约束兜底

提交遇到 `IntegrityError` 后回滚，再按用户和幂等键查询。哈希一致才返回；否则冲突。应用检查和数据库约束共同构成边界。

`start` 返回 HTTP 202，表示任务已登记。报告生成、校验和导出在 Worker 中继续，不属于提交接口完成的工作。

## 关键问题

1. 模型或请求体能不能填写 `tenant_id` 来扩大权限？真正身份来自哪里？
2. 为什么锁用户行和锁任务行解决的是不同问题？
3. 请求超时后前端换一个幂等键重发，会破坏什么保证？
4. API 已返回 202，随后报告生成失败，为什么不矛盾？

<details>
<summary>判定要点</summary>

应定位 `authenticate → create_task → RunContext` 的服务端身份链；说明准入串行化与执行领取的区别；同键重放只覆盖同一次建任务；202 不承诺最终报告成功。还应说明前端 pending key 只保存在当前组件内，页面重载后不能假定仍复用原键。

</details>
