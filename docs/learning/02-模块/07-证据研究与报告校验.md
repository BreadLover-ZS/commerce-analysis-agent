# 02 模块 · 证据、研究与报告校验

前置：[Agent 篇](06-DeepAgents工具与预算.md)。业务问题：一个报告看起来引用齐全，为什么仍可能错？怎样从最终结论回查原文和指标？

## Part A：先画数据流，再读校验器

```text
业务工具结果 / 文档片段 / 搜索片段
  → Repository.add_evidence：保存证据账本
  → evidence_package：选择来源和窗口，保留 manifest
  → ResearchSynthesis：发现、冲突、候选缺口
  → validate_synthesis + 逐项模型研究复核
  → draft：接收通过的研究或确定性摘录
  → ResearchReport：章节、Claim、MetricReference、限制
  → 指标程序渲染 + validate_report + 模型报告评审
  → 人工复核（可选）→ export
```

“模型研究复核”“模型报告评审”和“用户人工复核”是三个独立步骤。

## Part C：账本与上下文窗口不同

证据包含 id、kind、title、locator、excerpt、payload、content_hash 和获取时间。账本保存的是实际取得且经过长度限制的片段，不保证是整份原文；网页证据通常只覆盖搜索服务返回片段。哈希对应保存片段，不能证明来源本身真实正确。

`evidence_package` 将指标优先放入，文本按查询相关性排序并按来源种类轮转，控制来源数和字符数。默认最多 18 个来源、28000 字符；文本窗口通常最多 1800 字符；库存指标包只保留前 8 个条目及对应目录，完整结果仍在账本。

document 类型使用结构化身份计数：本地按 provider/document_id，RAGFlow 按 provider/dataset_id/document_id，每份文档最多两条，不受 PDF 页码、DOCX 段落或 XLSX 工作表 locator 变化影响。旧证据只对已知 URI 解析身份并标记 inferred；无法识别的身份记录 unknown，仍受总来源与字符预算限制，不能声称旧数据全部具备文档配额保证。

manifest 记录 selected_ids、excluded_ids、exclusion_reasons、truncations、窗口位置、身份推断/未知清单和预算。排除原因区分旧指标版本、文档配额、来源上限与字符预算。指标先经过 `authoritative_evidence`，同任务同工具同周期只用首份快照；旧版本留在账本但不能成为报告事实引用。清单让你知道模型实际看过什么。引用完整账本里的片段，不能自动证明模型上下文也包含该片段。

## Part D：研究发现要过两道门

### D1. 程序检查引用

`validate_synthesis` 要求发现 ID 不重复，support 指向适用文本来源，quote 是保存 excerpt 的逐字子串；conflict 至少引用两个不同 locator。

这是引用有效性检查。两段摘录都存在，也可能被错误拼接成因果；两个来源也可能只是互补规则，并未冲突。

### D2. 模型逐项评审

`ResearchSemanticReview` 对每个发现 ID 恰好返回 supported/unsupported/uncertain；`research_review_issues` 拒绝漏 ID、重复 ID、未知 ID 和越界的缺口索引。unsupported 或 uncertain 均不能算通过。

研究生成器只收到文本原文，另有 `business_fact_index` 告诉它整个任务已经拿到哪些经营事实键。否则它可能因为文本里没写库存，就错误声称“整个任务缺少库存快照”。这个索引不让文本研究伪造经营数值或 quote。

首次候选未通过后最多业务修正一次；仍失败时只保留 `excerpt_synthesis` 的确定性摘录，并记录研究验证失败。被拒研究不能悄悄传给 draft 当作已核准结论。候选 gaps 会保存在研究结果，但不会在 live 中强制照抄成报告限制。

## Part E：报告 Claim 有三类

| kind | 责任 | 指标引用规则 |
| --- | --- | --- |
| fact | 呈现能核对的事实 | 可以含完整 MetricReference；指标句程序渲染 |
| analysis | 解释已有事实 | metrics 必须为空；使用 evidence_ids 指向依据 |
| recommendation | 提出待确认的建议 | metrics 必须为空；事实前提仍需支持 |

`metrics_only_on_facts` 在 Schema 层拒绝分析/建议携带指标。`metric_binding_issues` 再核对 evidence 类型、指标键、数值、商品、单位、周期与快照。`render_bound_metrics` 只对完整有效绑定生成权威事实句；非法引用不会被悄悄修成正确引用。

文档中的“60 天”可以用文本 quote 支持，但不能冒充工具 `fact_catalog` 里的经营计算引用。工具参数中的 lead_days/overstock_threshold_days 则需要对应完整指标引用，不能只在自由文本中写数字。

## Part F：`validate_report` 能证明到哪

程序检查章节顺序、空章节具体限制、重复结论 ID、引用存在、事实与分析有依据、指标绑定和渲染文本、自由文本数字来源、模拟资料标注等。

程序通过后，live 可让模型核对结论及 limitations 与证据是否支持。模型评审结果中的 ID、索引还要再校验。评审可能漏判或误拒，`semantic_status=model_reviewed` 只说明执行过相应评审，不等于业务真实。

不要把“未展示一个指标”和“声称该指标不存在”混为一谈；也不要把“本次没取得资料”扩大为“企业没有资料”。这些都是本项目历史失败里出现过的区别，详见[真实模型记录](../../16-usage-receipts-and-provider-check.md)。

## Part G：一次人工回查怎样做

下载四个 JSON/Markdown 产物，任选一条库存事实和一条内部规则发现：

1. 在 `report.json` 找 Claim 的 kind、evidence_ids、metrics。
2. 去 `evidence.json` 找同 ID 的 payload.fact_catalog 或 excerpt/locator。
3. 去 `research.json` 对照 finding.support 和逐项 review。
4. 看 evidence_selection，确认来源是否入包、有无窗口截断。
5. 对照任务周期和库存快照，再核对报告分析是否超出事实。
6. 单独记录“引用有效”“数值对应”“推理支持”“章节完整”，不要只给一个笼统 PASS。

<summary>判定要点</summary>

哈希只用于片段一致性；引用存在不保证支持关系。漏评不能当作默认支持；金额不等于利润。degraded 是任务交付状态，fallback 是报告生成路径，research_validation 是研究门槛，三者各描述不同层。
