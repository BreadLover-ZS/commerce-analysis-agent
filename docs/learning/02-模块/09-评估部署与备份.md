# 02 模块 · 评估、部署与备份

前置：[前端篇](08-前端与任务诊断.md)。业务问题：代码有测试、模型有回答、容器有配置，分别还差什么才算验证？

## Part A：先区分验证层次

| 入口 | 主要证明 | 不能直接推导 |
| --- | --- | --- |
| 业务/权限/校验单测 | 给定输入下的确定性行为 | 外部模型效果 |
| 真实 SDK + ScriptedCommerceModel | Schema、工具、Skill、委派与预算协议可达 | 模型会正确研究和评审 |
| 32 条 demo 评估 | 固定样例的业务契约 | 全量真实用例通过 |
| 真实 PG 测试 | 实际数据库事务、行锁、接管与恢复 | 用户生产库已恢复 |
| 三个真实模型教学单例 | 对应实现下单例自动检查与人工核对 | 稳定通过率、多 Agent 收益 |
| 20 任务隔离 demo 负载 | 该机器下提交到 PDF 的教学链路 | 生产容量、模型响应时间 |
| 远端容器 CI | 对应提交的隔离构建/烟测/恢复 | 目标服务器 HTTPS 已验收 |

历史批次以[交付记录](../../18-python-delivery-validation.md)和[模型记录](../../16-usage-receipts-and-provider-check.md)为准，不要把本文命令理解为这些批次已被重新执行。

## Part B：读评估器怎样避免“有文件就 PASS”

顺序：[cases.jsonl](../../../evaluations/cases.jsonl) 任选一条 → [fixtures.py](../../../evaluations/fixtures.py) 的 `prepare_case` → [run.py](../../../evaluations/run.py) 的 `load_cases/evaluate` → `research_execution_ok/research_semantics_ok`。

`evaluate` 建临时 SQLite 与样例，按指定策略逐个建任务、运行 Worker，保存请求、任务、证据、事件、研究与检查项。检查包括完成状态、章节、预期指标、内容约束、来源实际使用、真实执行与研究语义门槛。

任一自动检查失败后停止后续用例，记录 dataset_size、executed、passed，保留失败证据。人工核验仍由操作者逐项执行；评估器不会自动代替人检查“自动 PASS 但业务错误”的情况。

离线练习命令从仓库根目录执行：

```bash
AGENT_MODE=demo KNOWLEDGE_PROVIDER=local uv run python -m evaluations.run --mode demo --strategy workflow \
  --output evaluations/results/learning-demo-01.json
```

结果文件名选择未使用的名称；评估器的 output 会写入文件，不能用历史证据路径试跑。`--mode live` 会产生真实请求，学习主线不需要运行。文件中保留的业务材料也不应无审查上传 Git。

## Part C：多 Agent 比较器为什么要求严格

[review.py](../../../evaluations/review.py) 中，`annotation_template` 生成空分数；`compare_runs` 要求同数据集、样例、实现和模型预算配置，三个策略各至少三个不同完整轮次。

人工标签绑定结果文件字节哈希，分正确性、证据支持、完整性、工具行为四项，0～2 分，非满分需要说明。缺标签、缺轮次、混用 demo 或不一致配置都拒绝给收益结论。外部来源未冻结时，差异也不能全归因于 Agent 架构。

阅读 [test_evaluation_review.py](../../../tests/test_evaluation_review.py)，找出一个“理应拒绝比较”的断言。不要为凑轮次复制同一个 run_id。

## Part D：PostgreSQL 与 CI 从哪里读

| 源码/配置 | 要回答的问题 |
| --- | --- |
| [test_embedded_postgres.py](../../../scripts/test_embedded_postgres.py) | 如何自建临时 PG 并把 URL 传给子 pytest |
| [test_postgres.py](../../../tests/test_postgres.py) | 为何使用随机 schema、非超级用户，并在结束后清理 |
| [ci.yml](../../../.github/workflows/ci.yml) | backend/browser/container 三个任务各做哪些检查 |
| [docker-compose.yaml](../../../docker/docker-compose.yaml) | 数据库、迁移、API、Worker、前端及卷怎样连接 |
| [production.yaml](../../../docker/production.yaml) | 目标环境与 HTTPS 覆盖配置 |

没有 TEST_POSTGRES_URL 时，PG 测试明确跳过。若本机支持临时 PG，可按部署文档运行：

```bash
uv run --with pgserver==0.1.4 python scripts/test_embedded_postgres.py tests/test_postgres.py
```

它可能下载测试运行依赖，并创建本地临时服务；系统限制监听端口时应报告环境阻塞。外部测试 URL 只能指向可丢弃测试服务，因为测试会创建、删除数据库对象。

## Part E：备份恢复读“条件—动作—失败后状态”

从 [backup_postgres.py](../../../scripts/backup_postgres.py) 按 `create_backup → _validate_bundle → _require_empty → restore_backup` 阅读。SQLite 对应 [backup_local.py](../../../scripts/backup_local.py)，公共路径和文件校验在 [backup_common.py](../../../scripts/backup_common.py)。

| 时点 | 当前要求/行为 |
| --- | --- |
| 备份前 | 停 API、所有 Worker 和其他写入者；不得有 running/cancelling 任务 |
| 备份内容 | 业务库、检查点、运行文件与哈希清单；不含 `.env` 和数据库角色 |
| 恢复前 | 可信备份、空目标库、新运行目录；不要提前 init 写入表 |
| 数据库恢复 | 官方 pg_restore，单事务、失败即退出，不删除覆盖旧库 |
| 文件发布失败 | 数据库可能已提交，保留暂存文件，先核对状态再处置 |

`--services-stopped` 是操作者声明，程序不能证明所有外部写入者都已停止。哈希检查损坏，不能证明备份来源可信。数据库提交和文件发布也不是一个事务。

第一轮通过 [test_postgres_backup.py](../../../tests/test_postgres_backup.py) 学恢复场景，不对现有运行库直接执行 create/restore。实际命令与故障处理统一看[部署文档](../../05-deployment.md)，避免学习文档维护第二份生产操作手册。

## 关键问题

1. 离线 32/32 和三个真实单例通过，分别可以怎样描述？
2. 实际只执行了 1/32 用例就失败，为什么不能写全量通过率？
3. 为什么恢复前不应先运行 `app.cli init`？
4. 数据库恢复成功但文件发布失败时，直接重跑为什么危险？

<details>
<summary>判定要点</summary>

应明确样例与模型质量边界、executed 与 dataset_size 的区别、空目标库前提，以及数据库已提交的可能性。报告 PASS/FAIL/BLOCKED/UNTESTED 时，要具体到验证层和环境。
