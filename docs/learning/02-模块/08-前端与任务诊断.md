## Part B：提交怎样避免网络重试重复建任务

`submit` 先确保会话，构造 payload，把 `JSON.stringify(payload)` 作为前端指纹。内容未变且上次请求尚未确认时，保留原 UUID 幂等键；成功后清空 pendingSubmission。

后端另计算规范化请求哈希并执行数据库幂等，前端指纹不代替后端约束。pendingSubmission 是组件内存，不跨刷新持久化；刷新后重新点击不能保证仍是原提交尝试。

公开词单独填写，只有选择 web 时才发送。表单中的来源与策略会进入 TaskRequest，但最终执行仍遵守服务器和图内约束。

## Part C：当前使用轮询，SSE 是另一接口

App 在登录后约每 2 秒刷新任务列表。选中任务时，约每 1.2 秒并发请求详情和游标后的事件，取得详情后再读证据，最后一起更新页面；fetching 标志避免该 effect 的轮询重叠，disposed 标志避免切换后旧结果覆盖新页面。

这个读取顺序有业务含义：报告只引用已经提交、保留在账本中的证据。若三个接口全并行，证据查询可能早于报告提交，详情却读到新报告，点击引用便找不到来源。先读报告再读证据消除了这个已复现的窗口；[diagnostics.spec.ts](../../../frontend/e2e/diagnostics.spec.ts) 中的延迟用例专门验证该时序。

事件响应有 cursor，前端按 event.id 去重。刷新后 cursor 从零重新取历史；当前选中任务 ID 按用户邮箱保存在 sessionStorage。事件可靠恢复依赖后端持久化，不是只靠浏览器保留一个数组。

API 另有 `/stream` SSE 游标重放入口，但当前 App 没有用 EventSource 消费它。面试时不能把后端具备 SSE 接口说成前端已采用 SSE 实时 Token 流。

## Part D：失败诊断读优先级

`failureDetails` 先处理 runtime_budget、model_or_tool_budget、recovery_exhausted 等终态原因，再匹配同 error_type 的最新 model_error 事件，映射安全类别。

| 情况 | 展示原则 |
| --- | --- |
| 总时限到达 | 优先解释任务总时限，不被较早的可恢复服务错误覆盖 |
| 模型超时 | 只展示已确认的 connect/read/write/pool；未知时明确未知 |
| 用量不完整 | 提醒费用未知，重新提交可能产生额外费用 |
| 研究复核失败且报告存在 | 说明退回原文摘录，不能当成完整研究通过 |
| 未识别错误 | 保留任务编号和错误代码，不猜底层原因 |

后端 [provider_error_data](../../../app/core/errors.py) 只输出安全的固定类别等字段，避免把原始服务错误体、请求和密钥传到页面。不要为了排查而把完整 provider exception 加回用户界面。

## Part E：一次前后端联合排查

在隔离 demo 中打开浏览器 Network，提交一次需要人工复核的任务：

1. 看 POST `/api/tasks` 是 202 还是校验错误；记录返回 ID。
2. 看详情中的 status，确认有 queued/running/waiting_review。
3. 看 events 的 after 与 cursor，判断是否一直请求同一批事件。
4. 点依据，按 evidence_id 对照后端响应和页面。
5. 审批时检查 `/review` 的 approved 布尔值；随后看 Worker 是否继续。

调试截图和 HAR 可能包含 Cookie、CSRF 和文档，保留笔记时只记录必要字段，不提交认证头。

## 关键问题

1. 刷新后历史事件从哪里恢复？sessionStorage 保存了什么？
2. `fetching`、`disposed` 和事件 ID 去重分别防什么？
3. 后端已提供 SSE，为什么当前前端仍应描述为游标轮询？
4. 错误诊断为什么先看终态 error_code，再看历史服务事件？

<details>
<summary>判定要点</summary>

应指出服务端事件表、当前任务选择、请求防重入、旧响应防覆盖与事件去重的不同职责。终态总时限优先，否则可能把当前失败错误归因为早已处理过的工具异常。

</details>
