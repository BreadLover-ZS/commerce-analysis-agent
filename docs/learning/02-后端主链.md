# 后端主链：从提交到恢复

前置：[总览](01-总览.md)。按“基础 → 数据 → 请求 → Worker → 页面”读源码，模型部分接着看 [Agent与证据](03-Agent与证据.md)。

## 1. 只补读项目需要的 Python

| Java 中熟悉的概念 | 本项目对应 | 注意点 |
| --- | --- | --- |
| Controller、DTO、参数校验 | FastAPI、Pydantic `BaseModel` | Schema 合法不代表有权限或业务正确 |
| 实体、DAO、事务 | SQLAlchemy、`Repository` | 数据库 Session 与登录会话不同 |
| 配置类 | `Settings(BaseSettings)` | 环境变量与 `.env`；`get_settings` 有缓存 |
| 后台消费者 | Worker 轮询任务表 | 没有 MQ ACK |
| 流程状态 | `ResearchState(TypedDict)` | 是字典类型说明，没有 Pydantic 运行时校验 |

先打开 [schemas.py](../../app/research/schemas.py)、[repository.py](../../app/storage/repository.py)、[worker.py](../../app/tasks/worker.py)，看懂这些形态：

- `def method(self, ...)` 是实例方法；`build_workflow` 内的节点函数是绑定当前任务对象的闭包。
- `str | None` 表示可空，`list[str]` 表示字符串列表；普通类型提示不会自行执行校验。
- `request.model_dump(mode="json")` 转成 JSON 兼容字典；`ResearchReport.model_validate(...)` 重新解析校验。`model_copy(update=...)` 不能替代重新校验。
- `with repo.session() as db` 管资源；是否提交要看 `commit/rollback`，不能假定退出就提交。
- `await` 在等待时交出执行机会，不会把同步 SQL 自动变成异步 I/O。

Worker 用 `await asyncio.to_thread(repo.claim)` 避免同步查询直接阻塞事件循环，用 `create_task` 协调执行与心跳，用 `asyncio.timeout(remaining)` 限制剩余执行时间。取消等待不保证底层线程立即停止，所以写入仍需检查租约。

`StaleLease`、`TaskCancelled`、`BudgetExceeded` 分别表达租约失效、取消、预算限制。工具不能捕获所有异常后统一返回空列表；检查节点的重新抛出和 Worker 的 `finally` 清理。

## 2. 启动时有哪些进程和数据

常规启动见 README。需要不保留数据的练习环境时，从根目录启动隔离后端：

```bash
uv sync --frozen --python 3.12
KNOWLEDGE_PROVIDER=local uv run python scripts/dev_backend.py --ephemeral --port 8091
```

另一个终端启动前端：

```bash
cd frontend
pnpm install --frozen-lockfile
VITE_API_PROXY_TARGET=http://127.0.0.1:8091 pnpm dev --port 5191 --strictPort
```

打开 [隔离工作台](http://127.0.0.1:5191)。`--ephemeral` 强制 demo，使用临时数据库、运行目录和本地账户，退出后清理；需要的报告先下载。脚本继承部分父环境，显式选择 local 可避免现有 RAGFlow 配置影响练习。

读 [dev_backend.py](../../scripts/dev_backend.py) 的 `main`：

```text
app.cli init：迁移、账户、演示数据
  → 子进程一：app.tasks.worker
  → 子进程二：uvicorn app.api.server:app
```

网页能打开不等于 Worker 正常。`/health/live` 检查 API 响应，`/health/ready` 还检查就绪条件。SQLite 业务库保存用户和任务；`data_dir/checkpoints.sqlite` 保存图进度；`data_dir/artifacts` 等保存运行文件。备份只复制业务库会漏数据。

## 3. 默认经营复盘的数据链

| 顺序 | 源码入口 | 关注点 |
| --- | --- | --- |
| 1 | [CommerceDataPanel.tsx](../../frontend/src/CommerceDataPanel.tsx) | 场景 / CSV 预览、确认版本、质量检查 |
| 2 | [datasets.py](../../app/commerce/datasets.py)：`parse_csv/stage_dataset/commit_dataset` | 格式、内容哈希、暂存确认、用户归属 |
| 3 | [repository.py](../../app/storage/repository.py)：`create_task` | 绑定本人已确认的 `dataset_id` |
| 4 | [tools.py](../../app/research/tools.py)：`ToolGateway.metrics` | 服务端上下文与指标证据 |
| 5 | [review.py](../../app/commerce/review.py)：`dataset_review/calculate_review` | 同一版本计算本期、前期和贡献 |

新入口强制 `profile=commerce_review`、`sources=[sales]`、`strategy=workflow`。`commerce_datasets` 保存不可变 payload，确认后没有覆盖更新 API；新导入和旧业务表更新不改变已有任务的数据版本。

CSV 一行对应商品一个记账日，金额为整数分、件数为非负整数。商品启用日起每天应显式记录，零销量也要有行；未建模停报/下架生命周期。格式与额度查 [数据契约](../21-commerce-review-development-validation.md#3-csv-数据契约)。文档附件不等于销售 CSV 导入。

必须能手算并解释：

```text
净销售额 = 支付金额 - 本周期记账退款金额
净销量 = 支付件数 - 本周期退款件数
退款件数比例 = 本周期退款件数 / 本周期支付件数
商品变化贡献 = 本期商品净销售额 - 前期商品净销售额
```

净销售额未扣成本，不是利润。退款按记账周期统计，不是同一批订单最终退款率；跨期退款可能超过同期支付。分母不可用时不生成比例，不能补零或截成 100%。金额累加使用整数分，Decimal 格式化为元。

前期是紧邻的同长度窗口。两期覆盖不完整或无适用商品时，不输出变化贡献；前期金额非正时保留变化金额、不算变化率。商品、品类贡献分别加总到整体变化。例如前期 40 元、本期 38 元，A 贡献 -10 元、B 贡献 +8 元，合计 -2 元。

## 4. 高级库存路径的差别

[service.py](../../app/commerce/service.py) 的 `sales_summary/inventory_risks` 读旧 `products/daily_sales`，与不可变数据集分开。管理员 JSON 导入走 [importer.py](../../app/commerce/importer.py)，不向模型开放写工具。

```text
collect → ToolGateway.metrics → Repository.metric_snapshot
        → 无已存结果才计算 → add_evidence
库存覆盖天数 = 快照库存 × 周期天数 / 周期净销量
```

九月教学样例中，保温杯库存 20、净销量 324、周期 30 天，覆盖约 1.85 天；与配置提前期 7 天比较得到缺货风险。这是历史销量估计，配置提前期不等于供应商实际交期。

- 旧工具按全部商品每天应有一行检查覆盖，没有新数据集的启用日规则。无记录、部分记录、完整零销量须区分；缺数、无正净销量或快照不适用时，不强算覆盖。
- 风险先排序再截取，避免高风险被 limit 隐藏。SQL 排序与 Python 分类使用未舍入的交叉乘积，展示时才格式化。
- `fact_catalog` 保存指标键、值、商品、单位、周期、快照，只检查“数字存在”会漏掉商品错配。
- 同任务/工具/周期复用首份可用快照。旧版本保留但不能成为权威事实；空读取仍可能重放，销售与库存没有跨工具统一数据库快照。需要最新数据应新建任务。

## 5. 请求怎样认证并入队

阅读顺序：[App.tsx](../../frontend/src/App.tsx) 的 `submit` → [api.ts](../../frontend/src/lib/api.ts) → [server.py](../../app/api/server.py) 的 `start` → [auth.py](../../app/core/auth.py) 的 `authenticate` → `Repository.create_task`。

Cookie 存随机 token，数据库 `AuthSession` 只存哈希与到期时间；密码用带盐 PBKDF2。修改请求还检查 Origin 和 CSRF。用户、组织来自服务端登录态，模型和请求体不能自己声明身份。

任务、事件、证据、产物按用户检查；内部规则按组织、私有附件按用户与会话过滤。下载用 `artifact_id`，检查归属、安全路径和文件存在；接口没有逐次重算文件哈希。越权或不存在统一返回 404。

`create_task` 分四段：规范化请求算哈希 → 锁用户并查会话/数据集归属和活跃上限 → 写任务与 queued 事件 → 唯一约束兜底，冲突回滚后再核对哈希。任务建立时固定 mode，避免配置切换把排队 demo 变成 live。

| 提交情况 | 行为 |
| --- | --- |
| 同用户、同幂等键、同请求 | 返回已有任务 |
| 同用户、同键、不同请求 | 409 冲突 |
| 内容相同但新键 | 可以新建，仍受准入限制 |

202 只表示登记，不保证报告成功。前端 pending key 在组件内存中，刷新后不保证复用；后端哈希与数据库约束是最终边界。用户行锁串行化准入，Worker 的任务行锁负责领取，二者不同。

登录限流依赖可信代理链；Caddy → Nginx → Uvicorn 的信任和转发头配置见 [部署文档](../05-deployment.md)。不要为处理认证错误而关闭保护。

## 6. Worker 怎样执行和接管

有序入口：`Repository.claim` → `validate_task_lease/_fenced` → `Worker.run/process` → [LeaseFencedSaver](../../app/tasks/checkpoints.py) → `finish/cancel/review`。

PG 用 `FOR UPDATE SKIP LOCKED` 跳过已锁任务，再按旧 token 和状态条件更新，成功才生成新 `lease_token` 和 `RunContext`。SQLite 的短写事务与条件更新不能证明 PG 行锁语义。

`RunContext` 是服务端不可变上下文，绑定任务、用户、组织、会话、租约。`task_id` 标识业务任务与主图线程，`lease_token` 标识本次执行者，不能互代。

```text
queued → running → waiting_review → queued → running → succeeded / degraded / rejected
           ↓
         failed
running → cancelling → cancelled
queued / waiting_review → cancelled
```

API 复核只保存决定并排队，由 Worker 恢复。`degraded` 表示带缺口交付，要继续看限制、研究验证与回退标志。

Worker 约每 `lease_seconds / 3` 续租。截止时间持久化，崩溃接管不重新获得完整时限；人工等待不计执行耗时，批准后按累计耗时算剩余预算。领取次数与模型请求次数是不同计数。

```text
A 领取 token=A → 发出外部请求 → 心跳停止、租约过期
B 领取 token=B → 从检查点继续
A 请求晚到 → 写入前检查 token → StaleLease，拒绝提交
```

业务写和 checkpoint/pending writes 都要保护，检查租约到 Saver 写完之间持续持有任务锁。主图线程是 `task_id`，研究子图是 `task_id:research`，不允许写其他线程。

业务事务与检查点、文件写入与登记都没有合成一个原子事务。首份快照、稳定证据键、租约独立目录、同步检查点限制重复副作用，但不能撤销外部请求或费用，不能宣称 exactly-once。恢复发现模型请求未回执时，标记用量未知并停止新模型请求。

## 7. 从页面找到后端阶段

读 `App` 的 `useState/useRef/useEffect`、[types.ts](../../frontend/src/types.ts)、[TaskDiagnostics.tsx](../../frontend/src/TaskDiagnostics.tsx)。state 驱动展示，ref 保存游标和 pendingSubmission，effect 管加载、轮询及清理。

当前 App 用游标轮询；后端有 SSE 接口不代表前端在流式展示 Token。事件在服务端持久化，刷新后重读并按 ID 去重；sessionStorage 保存按用户区分的选中任务 ID。

详情与事件可并发读，拿到详情后再读证据，避免新报告引用尚未读到的账本。`fetching` 防轮询重叠，`disposed` 防切换任务后旧响应覆盖。

错误诊断先看终态 `error_code`，再找匹配的最新模型错误事件；总时限不能被旧异常掩盖。超时阶段未知就明确未知，不把原始服务错误体或密钥输出到页面。
