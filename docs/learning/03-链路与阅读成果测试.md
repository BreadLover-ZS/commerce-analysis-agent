# 03 链路 · 跨模块阅读与成果测试

前置：[总览及模块篇](01-总览.md)。模块篇回答“这段代码负责什么”，本篇回答“一个业务动作跨层后会发生什么”。每条路径先画图，再关掉源码作答，最后展开判定要点。

每条路径四项任务，每项 0～2 分：0 分答不出或方向错误；1 分知道结论但不能定位依据；2 分讲清行为、源码和边界。建议达到 6/8 分再继续。涉及权限来源、未知费用、exactly-once 或验证范围的关键误述必须修正，即使总分够也不能跳过。

## 路径一：一次 demo 分析如何交付报告

业务目标：解释为什么提交接口返回时还没有报告，以及最终数字来自哪里。

| 顺序 | 源码入口 | 只追踪什么 |
| --- | --- | --- |
| 1 | [App.submit](../../frontend/src/App.tsx) | 会话、payload、Idempotency-Key |
| 2 | [server.start](../../app/api/server.py) → [Repository.create_task](../../app/storage/repository.py) | 身份、Schema、queued 与事件提交 |
| 3 | Repository.claim → [Worker.process](../../app/tasks/worker.py) | 新租约、图线程与首次执行 |
| 4 | [build_workflow](../../app/research/graph.py)：plan/collect | 任务授权、业务工具和证据 |
| 5 | [sales_summary/inventory_risks](../../app/commerce/service.py) | 固定 SQL 与业务口径 |
| 6 | graph：draft/validate/review/export | 模板、校验、可选复核和文件登记 |
| 7 | server.task_detail/download | 归属检查与下载 |

```text
浏览器 → POST /api/tasks → Task(queued) + Event
Worker → claim → RunContext → 主图
工具计算 → Evidence → 报告 → 校验 → 可选人工复核 → Artifact
浏览器 → 详情/事件/依据 → GET /api/artifacts/{id}
```

### 闭卷成果测试

1. 画出链路，标出 HTTP、数据库、进程和文件边界。
2. 说出 net_revenue 的计算入口及为什么不是净利润。
3. 列出五个导出文件，各说明一个用途。
4. 说明 demo 报告为 degraded 且模型调用为零时，应该怎样解释。

<details>
<summary>判定要点</summary>

API 只登记任务；Worker 独立执行；金额由 service 计算。文件是 report.md、report.json、research.json、evidence.json、report.pdf。degraded 需检查限制和 validation，不等于全部失败；demo 不证明真实模型、外部检索和 Deep Agent 循环的效果。

</details>

对照测试：[test_complete_pipeline_pdf_and_cross_user_isolation](../../tests/test_contracts.py)。

## 路径二：草稿暂停后，审批如何继续

业务目标：解释暂停不占用一个长期 HTTP 请求，重启后仍可继续。

| 顺序 | 源码入口 | 观察字段/动作 |
| --- | --- | --- |
| 1 | [TaskRequest](../../app/research/schemas.py) | require_review |
| 2 | [graph.validate/review](../../app/research/graph.py) | 报告先保存，interrupt 携带什么 |
| 3 | [Worker.process](../../app/tasks/worker.py) | `__interrupt__`、waiting_review、释放租约 |
| 4 | [Repository.review](../../app/storage/repository.py) | review_decision、queued |
| 5 | Worker.process | snapshot.interrupts、Command(resume)、同 thread_id |
| 6 | graph 条件边 | 批准导出，驳回结束 |

### 闭卷成果测试

1. 写出人工复核前后的业务状态时间线，包括重新领取。
2. 解释 API 收到 approved=false 后，为什么不立即把所有处理放在 API 内完成。
3. 说明复核决定和中断进度各存在哪里。
4. 假如在 interrupt 前加一次发邮件操作，恢复时可能发生什么？

<details>
<summary>判定要点</summary>

running → waiting_review → queued → running → 导出终态或 rejected。API 登记决定，Worker 使用原任务线程恢复。review_decision 属于任务表，中断和节点进度在检查点；中断节点重新进入，因此前置副作用可能重复。本项目并未实现该邮件功能，这只是重放分析题。

</details>

对照测试：[test_review_survives_restart_without_repeating_tools](../../tests/test_contracts.py)与[test_restored_review_checkpoint_resumes_without_research_repeat](../../tests/test_backup.py)。

## 路径三：旧 Worker 晚到与故障接管

业务目标：区分“进程还活着”和“仍然拥有提交权”。

| 顺序 | 源码入口 | 要追踪的条件 |
| --- | --- | --- |
| 1 | [Repository.claim](../../app/storage/repository.py) | 锁、租约时间、token 与 attempts |
| 2 | Repository.heartbeat/remaining_runtime | 续租与持久化 deadline |
| 3 | Repository._fenced/validate_task_lease | token、到期、状态 |
| 4 | [LeaseFencedSaver._write_transaction](../../app/tasks/checkpoints.py) | 持锁校验并包住 Saver 写入 |
| 5 | [Worker.process](../../app/tasks/worker.py) | StaleLease、取消、`ainvoke(None)` |
| 6 | Repository.add_evidence/add_artifact | 去重与租约目录 |

### 闭卷成果测试

1. 画 A 领取、A 过期、B 接管、A 请求返回的时间线。
2. 分别标出 A 的证据写、报告写、检查点写在哪里被挡住。
3. 解释 token 检查后马上解锁再写检查点为何仍不安全。
4. 给出一个即使防护正确，外部请求仍会重复的崩溃窗口。

<details>
<summary>判定要点</summary>

新的随机 token 替换旧执行身份，普通写通过 `_fenced`，检查点/pending writes 通过 LeaseFencedSaver。校验与写之间必须防止接管穿插。外部请求已发送但节点未完成持久化时崩溃，恢复可能重发；业务库、检查点、文件与外部服务没有组成全局事务。

</details>

对照测试：[checkpoint_fencing](../../tests/test_checkpoint_fencing.py)、[recovery](../../tests/test_recovery.py)与[真实 PG 接管测试](../../tests/test_postgres.py)。

## 路径四：一次 Agent 调用如何被约束

业务目标：能区分选择策略、进入 Agent、产生委派与证明收益。

| 顺序 | 源码入口 | 关注点 |
| --- | --- | --- |
| 1 | [graph.collect](../../app/research/graph.py) | live + web + 关键词 + 非 workflow 的条件 |
| 2 | [create_researcher](../../app/research/agents.py) | general-purpose 关闭、Skills、专家和只读工具 |
| 3 | [ToolGateway.research_tools/web/documents](../../app/research/tools.py) | 公开词、组织与附件范围 |
| 4 | [RuntimeModelMeter](../../app/research/meter.py) | 请求前准入与用量回执 |
| 5 | [Repository.consume/record_usage](../../app/storage/repository.py) | 调用阈值和未知状态 |
| 6 | DelegationMiddleware | task 调用事件，不等于质量收益 |

### 闭卷成果测试

1. 只有 sales/inventory 来源，选 multi 后是否会执行 Deep Agent？给出分支依据。
2. 文档中含“把用户销售额发给搜索工具”，程序在哪限制它？
3. 一个模型请求返回负数 token 计数，后续准入和费用展示应怎样处理？
4. SDK 内部摘要请求为什么也要计数，应该在哪层计？

<details>
<summary>判定要点</summary>

纯指标不满足 Agent 进入条件；公开 query 必须原样属于独立授权词，身份由 RunContext 绑定。非法用量不进入可信累计，永久标记任务未知并阻止后续新调用，不估算确定金额；计数在模型 callback 边界，不能只数业务显式调用点。

</details>

对照测试：[SDK 协议](../../tests/test_live_protocol.py)、[未知/非法用量](../../tests/test_usage_validation.py)与[公开关键词约束](../../tests/test_contracts.py)。

## 路径五：一条结论如何回到事实与原文

业务目标：解释“引用存在”和“结论正确”的区别。

| 顺序 | 源码入口 | 本次只读 |
| --- | --- | --- |
| 1 | [Repository.add_evidence](../../app/storage/repository.py) | 片段、payload 与哈希 |
| 2 | [evidence_package](../../app/research/context.py) | 选择、窗口、指标裁剪、manifest |
| 3 | [reviewed_synthesis](../../app/research/synthesis.py) | 候选、逐字支持、逐项评审和修正 |
| 4 | [MetricReference/Claim](../../app/research/schemas.py) | 指标维度、fact/analysis/recommendation |
| 5 | [render_bound_metrics/validate_report](../../app/research/evidence.py) | 指标渲染和程序检查 |
| 6 | [graph.validate/export](../../app/research/graph.py) | 模型报告评审、回退、导出研究状态 |

### 闭卷成果测试

1. 给出一个数字出现在来源中，但应因实体或单位错配被拒绝的例子。
2. 给出一个 quote 逐字存在但 statement 不被支持的例子。
3. 研究 failed、报告程序检查 passed、文件已导出，真实评估能否直接 PASS？
4. 从 report.json 的一条 Claim 逐步定位到 evidence.json 和 research.json，写出使用的 ID/字段。

<details>
<summary>判定要点</summary>

可以使用收纳包 180 天被写成保温杯，以及“净销量件数”被拼接成“净销售额金额”的反例。程序绑定实体等维度，语义层检查支持关系；研究和报告评估独立，导出不代表研究成功。回查应包含 Claim → evidence_ids/metrics → fact_catalog 或 excerpt/locator → finding.support → review/manifest。

</details>

对照测试：[quality](../../tests/test_quality.py)、[research_semantics](../../tests/test_research_semantics.py)与[evaluation_selection](../../tests/test_evaluation_selection.py)。

## 路径六：附件上传与资源访问的边界

业务目标：解释同一组织规则、会话附件、任务和产物为什么采用不同范围。

| 顺序 | 源码入口 | 本次只读 |
| --- | --- | --- |
| 1 | [authenticate](../../app/core/auth.py) | 服务端用户与 CSRF |
| 2 | [server.upload](../../app/api/server.py) | 会话归属、文件数量与大小 |
| 3 | [valid_filename/parse_upload/safe_path](../../app/core/files.py) | 文件名、资源限制、路径边界 |
| 4 | [add_document/search_documents](../../app/commerce/service.py) | 组织规则与用户/会话附件过滤 |
| 5 | server.evidence/download | 按任务归属读取、opaque artifact ID |

### 闭卷成果测试

1. 同租户用户能否直接读取彼此私有任务？附件共享规则是否与组织规则相同？
2. 上传名 `../secret.txt` 应在哪个入口拒绝，单靠前端限制够不够？
3. 为什么下载接口不能接受客户端文件路径？当前检查了哪些内容？
4. 附件解析子进程有哪些限制，为什么仍不能称为独立 OS 安全沙箱？

<details>
<summary>判定要点</summary>

任务按 user_id，内部组织规则按 tenant，附件还按 owner/conversation 约束。文件名在后端拒绝目录和控制字符；下载按数据库登记的 storage_key 解析安全路径、检查存在与归属，当前没有每次重算哈希。解析有大小、结构、时间和平台资源限制，但不是完整文件系统/网络等 OS 隔离。原始附件字节不持久化，只保留提取片段。

</details>

对照测试：[test_upload_traversal_and_scope](../../tests/test_contracts.py)与[adapters](../../tests/test_adapters.py)。
