## 根因与预检教训

这是本轮新增探针调度和能力说明的问题。HTTP 层只允许 2 次，Task 冻结的模型额度仍为 12，提示词先后显示 12/11 次模型调用、9/8 次决策调用。模型未获知真实资源边界；旧预检只覆盖了成功固定流程、首次失败阻断和账本，没有断言三个层次的预算一致。

`DiagnosticMetrics.refunds()` 已返回同范围支付金额、退款金额及各自两期和差额，但能力表遗漏支付金额。模型选择另查支付金额，随后还需要第三次查询退款，耗尽硬上限。正确的两个工具组合是逐商品排名与退款分析；程序已有同范围净额基线，可以建立九项范围金额恒等式见证。

历史教训据此转为具体门禁：

| 漏检 | 新检查 | 不允许的替代处理 |
| --- | --- | --- |
| 控制器与 Task 额度不一致 | 完整 SDK 探针断言冻结 Task 与 HTTP 同为 2；提示词显示 2 → 1 | 提高 HTTP 上限掩盖不一致 |
| 历史决策保留额度压缩小探针 | 显式冻结决策保留 0；缺省仍保留旧逻辑 | 全局更改旧版本默认值 |
| 能力表少报真实输出 | 对照工具事实目录断言 gross/refund；保留范围条件 | 提示模型猜测未取得的金额 |
| 只验证修复后正例 | 原取证顺序仍须 FAIL；高效顺序须严格 PASS | 放松 `amount_witness`、少算必答项 |
| 调用上限小于已知最低需要 | 读密钥前按问题、实体选择与覆盖检查结构下界 | 用已知题号硬编码答案或保证模型一定成功 |

## 实现

1. `model_decision_reserve` 为服务端设置，Task 创建时冻结为 `decision_call_reserve`；仅非默认值入库。旧 Task 不含此字段时，保留原有三次收尾保留及小额度兼容行为。非法保留值拒绝。
2. 新探针将 `max_model_calls` 设置为 HTTP 上限，并显式保留 0。诊断报告由程序收尾，不额外预留付费生成额度。规划器与图执行使用同一决策额度计算。
3. v16 仅在显式新策略下显示真实剩余额度、本次请求计数，以及退款工具已有的合并输出。提示范围金额恒等式与逐 SKU、品类、逐日义务不同，后者仍须独立取证。
4. 入口先检查结构最低调用数。H01 为 2，H13 为 3，固定完整流程为 2；这是已知下界，不是足够性或模型质量保证。
5. 失败父回执只有在源码改变、修复证据绑定该回执及新源码、本地验证通过后，才能承接新批次；实际消费和历史冻结始终累计。
