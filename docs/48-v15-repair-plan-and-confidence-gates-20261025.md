## 3. 先冻结语义，解决“什么算修好”

### 3.1 三个状态分别保存

1. **执行状态/stop_reason**：是否达到步骤/调用上限、正常完成、evidence_gap、UNKNOWN等。诊断的evidence_gap保持，不重命名掩盖缺数。
2. **所问数据可用性**：每项分别标记已核查可用、来源缺失、不适用、尚未查询/不明确；不能用一个coverage.complete=false概括库存快照、窗口、提前期三种条件。
3. **答复完整性**：建议为fulfilled、boundary_explained、incomplete。由程序根据固定请求契约、实际证据和报告展示计算，不能接收模型自报“完成”。

|请求|允许的答复完整性|必要证据|不能算完成的反例|
|---|---|---|---|
|完整两期金额、贡献、件数等|fulfilled|所有明确义务被正确取得并展示，所需对账完成|缺一对象/时期、只查询局部、报告截断必答项|
|明确询问缺口/限制，且已核查所有所问条件|boundary_explained|可回答项齐全；每个缺口有固定源/工具证明、范围与具体影响；无未查询项目|只写“资料不足”、未调库存工具、没确认快照是否存在|
|要求实际计算，但来源不足|incomplete，保留真实gap|显示已有事实与缺口，不造值|仅解释不能算就宣称原计算目标fulfilled|
|无成本却要求计算利润等|保留unsupported/gap边界，不计作支持的数值目标完成|明确缺什么、不能算什么，不替代成净额/销售变化率|把拒答或unsupported纳入正向计算成功率|
|已达到预算/协议无效/UNKNOWN|incomplete|保留已取得事实、未完成项和用量|将预算停止、invalid_decision或UNKNOWN算成边界答复完成|

H17-1可为stop_reason=evidence_gap、answer_status=boundary_explained，同时保留missing_lead_days；H17-2没有库存证据，必须incomplete。H06/H07若只问缺行对比较有什么限制，可以完整答边界；若问完整两期差额，则仍未完成。

请求意图只来自用户问题/明确产品选择和服务端绑定契约，不读取case_id、facet、Expected或作者答案。对混合/含糊问法保守处理，必要时澄清；不能用“出现限制/缺口两个字”就跳过数值要求。

### 3.2 统一“必须直接回答什么”

answer-contract-v4建议把每个required item的对象、指标、时期、单位、所需能力、展示要求写清；mandatory和optional分开：

- 明确要求“两期支付、退款、净额及差额”的新题，九项均为mandatory，两个流程都直接展示。
- 只问“三个变化额及对账”的新题，三项差额和恒等式是mandatory；两期绝对额可以是optional，不能暗中扩大作者表且仅惩罚一种流程。
- 记账退款占比需要对应期退款件数、支付件数、分母适用性及口径；不能由金额恒等式代替。
- 每个SKU、品类、逐日义务分开，TopK和汇总不能替代未覆盖对象；启用前不适用与启用后缺行继续区分。
- 资料缺失可证明unavailable，尚未查询只能not_queried；展示容量遗漏另列，不可转成来源缺失。

新题包的问法、作者表、生产请求契约、独立评分必须在发送前一致。作者表由人工按字面填写并以原始行求和核验，不能由生产解析器自动生成标准答案。

## 4. R1：最小提议Schema + 明确纠错，保留安全拒绝

### 4.1 新版本独立路由

新增diagnosis-v15/Prompt-v15、提议V3、报告schema4。Schema工厂仅依赖**保存的图版本、冻结的来源和请求目标**；不能随剩余预算、最新quotes、步骤数量动态改变Schema，避免恢复时schema_hash变化。

推荐维持tool/clarify/stop动作种类：

- Tool/Clarify分支不声明rule_interpretations，extra=forbid。完整实现中tool_name仍须来自冻结工具catalog，arguments仍由注册表6参数Schema及Gateway授权校验；原型里的str/dict仅用于验证形状，不能直接充当生产权限校验。销售/库存Task的Schema中完全不出现RuleInterpretation/QuoteReference定义。
- 仅授权文档且用户明确需要解释的Task，其Stop分支允许可选unverified解读。已有quotes与精确绑定仍在服务端校验，不能因为结构合法就通过。
- 只要求逐字引用时，不强制再发一次解释请求；H19/H20的引用/注入边界继续验证。
- 明确要求解释时，完成契约应保留相应未核验解释义务，不能在检索后自动停止而漏掉所问解释；无真实quote时不允许编造。

**两处Schema必须相同**：Gateway注入的system Schema及human context.schema均从同一工厂取得。不能给入口换V3，却让继承的planner_v12继续向模型展示StepProposalV2。

### 4.2 结构失败与语义拒绝都给安全、具体的correction

例如无规则源的工具提议携带规则解释：

```json
{
  "code": "rule_annotation_not_allowed",
  "field_path": ["rule_interpretations"],
  "required_action": "重新输出仅含当前动作允许字段的完整提议；不要生成规则解释或引用",
  "tool_executed": false
}
```

有文档但引用不匹配时，只说明引用必须来自当前Task已取得的有效quote；可提供有界的合法ID/hash元数据。不得回显异常中的原输入、任意解释、密钥、其他用户引用或供应商错误原文。

当前Gateway会把结构失败统一记validation_error且validated_output为空。v15需在不新增模型请求的情况下提取白名单错误类型/字段，写入已有ModelInvocation.error_code，再由图生成确定性correction；错误持久化后恢复也应得到相同反馈。无法安全定位时给有界通用纠正，不把未知结构内容当成合法工具参数。不要直接存str(parsing_error)。

- 有有效usage但Schema失败：保留已知用量，以FAILED/invalid提议继续受限纠正。
- 提供方异常/usage不完整：仍UNKNOWN并停止，不借“纠错”重发或退还token。
- 原非法提议仍REJECTED；只有之后独立形成、重新校验/授权的合法提议才能执行。
- 原模型响应、引用与拒绝理由可审计；不能通过删除rule_interpretations、放宽extra字段或自动执行“修过的原提议”制造成功。
- 纠正仍使用既有8步/10工具/12模型及token/时间上限；连续无效仍收束，SDK max_retries=0不变。

## 5. R2：程序判定答复完整性，并同步两种流程

新增独立completion_v15模块，根据固定请求义务、来源/工具状态及实际展示得到完整性，不通过删除missing_coverage字符串实现。

对每项至少保留：requirement_id、对象/时期、status、fact_refs或gap_proof_refs、是否已展示。已证明缺少提前期与未执行inventory_risk不同；当前金额可得、前期缺行和差额不可算也分别保存。

boundary_explained必须同时满足：

1. 请求确实是在询问这些边界，而非借边界词要求计算未知数值；所有子目标均有对应状态。
2. 可算/可查项目已完成，必须展示的数值已展示。
3. 每条缺口有当前固定源或已执行工具的确定性证明，含范围、时期、缺失类型和影响。
4. 没有not_queried、未澄清对象、报告容量遗漏、预算/协议/UNKNOWN导致的剩余工作。
5. 报告完整缺口清单与计数正确，未把缺数改成0或未核验因果。

诊断报告schema4保存answer_completion与结构化缺口，校验器根据完整证据重算，篡改完成标志必须拒绝。固定答复v4在其版本化证据中保存同一完整性投影，报告以程序生成的直接答复/完整性说明呈现；不假定固定报告原本有diagnosis stop_reason，也不向旧Report塞未声明字段。

前端显示“已说明资料缺口”与“仍有未核对项目”，同时保留原数据缺口；MD/PDF/JSON与复核预览一致。新字段仅服务端生成，旧schema1—3继续正常展示。

## 6. R3：按能力和证据认定等价，不能按工具名放行

v15增加accounting_amount_identity能力见证，由程序从注册表6的原事实推导；数值工具内核及注册表6输出保持不变。

合格见证必须满足：

- 同一绑定数据版本、用户授权、当前选择scope及明确两期，不能用初始大范围基线替代澄清后的单SKU。
- 支付、退款、净额所需事实均有真实evidence_id/metric_key，时期、单位和数值匹配；完整性/适用性允许所问比较。
- 使用整数分/Decimal，逐期net=gross−refund，差额delta_net=delta_gross−delta_refund精确一致；不靠浮点容差。
- 所需数值及恒等式说明在报告中实际出现，而非只存在工具内部或由用户倒推。
- 这只覆盖金额记账恒等式，不证明退款原因，不覆盖退款件数占比、分母效应、品类排行或日覆盖。

analyze_refunds是可提供该能力的一条路径；完整同范围的多指标compare_periods也可作为另一条路径，但不得因“调用过compare”就全局补上退款能力。

生产验证器和独立评分分别实现：前者从已授权事实构造/复核见证，后者从原始行重新计算并核对报告/引用；不能共享生产意图函数或直接相信生产输出的capability=true。当前单日原型只证明H03的可行性，实施时必须扩展到完整日历、启用边界、零值、缺行、多SKU及非相邻两期。

|T04|销售/库存Schema及Prompt|不暴露规则引用定义；system与context.schema一致|
|T05|有文档但尚无quote；外用户chunk；错误hash|全部拒绝，来源/权限不扩大|
|T06|授权文档+有效quote+明确解释请求|可输出unverified解释；不能升级适用性认证|
|T07|H19/H20引用/注入、恶意字段名与恶意产品名|quote-only不多要求解释；指令不增加动作、来源或预算|
|T08|同一输入：只问缺口 vs 要求完整数值|前者充分核查后可boundary_explained；后者缺数仍incomplete|
|T09|H17未查询 vs 真实缺lead|未查询不能完成；快照/窗口存在时代理仍可算，仅缺lead不能阈值比较|
|T10|只写泛泛“数据不足”、漏可得金额、漏缺口、展示截断|全部拒绝完成；缺口总数/省略披露准确|
|T11|H03同范围金额路径等价|两条合法工具路径均通过同一能力及展示检查|
|T12|金额相等但单位/币种/对象/时期/来源不一致；差一分|全部拒绝；不能靠相等数值或容差蒙混|
|T13|缺退款比较期；单SKU事实冒充总体；混不同bundle|不能证明恒等式或完整能力|
|T14|金额恒等式齐但问退款占比/分母/品类/逐日|仍必须完成额外能力，不能复用金额PASS|
|T15|明确九项问题，固定缺比较期支付额或任一项|两流程都FAIL；补齐后两流程都PASS|
|T16|只问三个变化额，明确可选两期绝对额|不额外强加九项；与作者定义一致|
|T17|零分母、负净额、新品不适用、启用后缺行、非相邻期|按已声明数值/适用性策略处理，不造0或新因果|
|T18|默认切换后旧Task幂等重试/等待恢复/复核|仍按保存版本，报告hash与批准不能移植到新内容|
|T19|v15响应落库/Step未落库、额度已耗尽|复用已保存结果，不重发、不重复扣费；Schema不随证据/预算漂移|
|T20|UNKNOWN、撤权、取消、旧lease/worker|停止或拒绝，不借纠错绕过安全与用量保护|
|T21|篡改answer_completion/能力见证/缺口证明|报告门禁与独立评分均拒绝|
|T22|新元数据把gap改target-only、删义务、删配对、改旧预算|发送前拒绝；新包未执行性可复核|

补充变形测试：交换SKU/排序/日期平移/整数缩放不应改变语义；增加授权外无关SKU不能改变选中范围；改变一个分子/分母应只影响对应能力。使用独立整数行期望，不照抄生产函数输出来断言。

补充缺陷挑战：在临时副本分别故意去掉引用绑定、scope/时期/单位条件、精确整数比较、固定义务检查及gap前置条件，相应负例必须检出。不是追求单测数量或“全绿”，而是证明测试能抓住预设的错误修法。

## 12. 如何判定“已有足够信心”

采用分层证据门槛，不把主观95%当成真实模型准确率或无bug保证：

|层次|当前状态|进入下一层必须补齐什么|
|---|---|---|
|根因可复现|已证实：原回执/源码、26项检查及4次协议替身Worker对照|实现前保留原失败，明确所有相邻负例|
|结构设计可行|已做13项最小Pydantic原型|完整Schema/Prompt一致性、错误码持久化、SDK解析与保存版本路由|
|局部修复正确|待实施|各R项独立正/负例及缺陷挑战通过；不能只跑脚本预设的正确提议|
|系统兼容正确|待实施|PG/HTTP、Chrome、旧版本、权限/UNKNOWN、历史评分及最终指纹完整证据|
|真实模型稳定达到门槛|未验证，不能提前保证|新未执行完整正式轮、三次全部保留、逐份业务审查及账本核对|

Confidence Check的重复实现/架构/官方接口与OSS实现/根因五维检查用于**本地实施准入**；有未确认的硬条件就先补证，不用平均分遮盖。当前可以按方案进入受控本地实现，但**不具备跳过上述阶段直接再次付费正式测试的证据**。

根因定位有足够依据；仍不确定的是模型在新Schema/反馈下的真实行为、复杂混合问法与完整兼容性。方案用明确退出条件和保守停止约束这些不确定性，不承诺任何模型100%遵守协议。最终本地验收报告应逐项列PASS/FAIL/UNTESTED，开放P0/P1为0且所有硬门槛通过后，才建议进入下一真实轮。
